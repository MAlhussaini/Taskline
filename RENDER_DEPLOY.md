# Render Starter deployment and recovery

This deployment creates a separate, publicly reachable instance; it does not synchronize with the existing Tailscale instance. Do not expose an unactivated owner account using the old code. Deploy only from a private repository after reviewing its history for private data. Render's persistent disk is accessible to a single runtime instance, not build jobs, cron jobs, or one-off jobs. Deployment with a disk briefly interrupts service.

- Python native runtime; `.python-version` pins the tested local version 3.11.2.
- Build: `pip install -r requirements.txt` (the runtime uses Python's standard library).
- Start: `TASKLINE_HOST=0.0.0.0 TASKLINE_PORT=$PORT python app.py`.
- Attach a persistent disk at `/var/data`; set `TASKLINE_DATA_DIR=/var/data` and `TASKLINE_OWNER_EMAIL` to the owner email. Set `TASKLINE_SETUP_TOKEN` to a unique random secret of at least 32 characters, generated using `python3 -c 'import secrets; print(secrets.token_urlsafe(32))'`. Set secrets directly in Render Environment, never in Git. `RENDER=true` is supplied by Render.
- Render starts only if the data directory is an actual mount and the database, uploads, state, and backups resolve inside it. Defaults: `/var/data/tasks.db` (SQLite WAL and SHM reside beside it), `/var/data/uploads`, `/var/data/private-data`, `/var/data/backups`. Do not set conflicting path overrides. No mount is accessed during build.
- On an empty database, Render requires the activation token and owner email to activate the owner. Remove the token environment variable after activation. Self-registration is disabled on Render; the owner or an admin can create users. Existing local behavior is unchanged. Use a strong owner password even though the configured minimum is six characters. Sessions persist and must be revoked manually if a device is lost. Login rate limits apply, but the apparent client IP behind Render's proxy may be shared; assess availability and rate limiting with real traffic before public rollout.
- New instances start empty. Existing data is not transferred automatically. To migrate, first create and verify a Taskline backup locally, transfer it securely to the Render disk through the service's authenticated shell, and use the existing backup verification and restore workflow. Run restore from the service shell with the same environment and disk; it takes the shared lock, creates a safety backup, and revokes sessions. Verify account access, users, tasks, images and integrity on the isolated instance before switching use. Never copy a live SQLite file alone: use the SQLite backup workflow to capture WAL changes.
- The current systemd backup timer is not provided by Render. Until an independently verified scheduler is installed, create and verify backups regularly through the admin account page or service shell (`python local_backup.py create`, `list`, `verify BACKUP_ID`). Export copies from `/var/data/backups` to a separate protected location and rehearse recovery. A backup stored only on the same disk is not disaster recovery. For restore, securely place a verified backup directory into `/var/data/backups`, run `python local_backup.py verify BACKUP_ID` and then `python local_backup.py restore BACKUP_ID` from the running service shell; re-login and check data. Keep off-disk copies, including a recent pre-migration backup. Do not use a Render cron job or one-off job to access the web service's disk.
- The disk incurs a separate charge. Run one service instance. Confirm the actual disk mount, login, admin authorization, isolation, session behavior and backup recovery on Render before using it for real data.

## Importing the committed export

The explicitly published export in `migration/` contains private account and planning data, including password hashes and session records. A public repository makes it downloadable to everyone. Remove it from public access if that is no longer intended; deleting a Git file does not erase existing history or copies.

Render does not import the export automatically. After mounting the disk and activating the fresh owner with the setup token, use the running service's authenticated shell to copy the export directory (including `manifest.json`) from `migration/` into `/var/data/backups/`. Run `python local_backup.py verify BACKUP_ID` followed by `python local_backup.py restore BACKUP_ID`, using the export directory name as `BACKUP_ID`. Restore invalidates sessions and replaces the initial owner and account data; sign in using the accounts from the export. Verify all users, tasks, and attachments. The existing local server and this snapshot will diverge after export; repeat migration before switching if local data changes.
